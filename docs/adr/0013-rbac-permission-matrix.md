# RBAC как матрица «действие × роль»

Права моделируются гранулярно: **Permission** = пара (ресурс, действие); **Role** = набор прав с уровнем доступа (No access / View / Edit). Роли аудит-иерархии (assessor / manager / approver) и системные пресеты (Admin, View-only Admin, Editor, Collaborator) — это заранее собранные наборы прав поверх одной матрицы, а не хардкод.

Категорий пользователей три (шире, чем две в исходном ТЗ): **внутренний аудитор**, **end user / респондент**, **MSP / внешний подрядчик**. Внешний аудитор — частный случай со scoped-доступом (аналог Auditor View).

Enforcement на двух уровнях: серверный guard проверяет право на каждое действие (не полагаемся на UI), а UI прячет/блокирует недоступное. Права всегда вычисляются в контексте тенанта и дочки ([[0003-shared-db-postgres-rls]]) — роль может действовать на уровне группы, дочки или департамента.
