# Две роли БД: приложение под app, миграции под owner

Следствие ADR-0003 (RLS), вскрыто в T-011: официальный postgres-образ создаёт стартового пользователя суперпользователем, а суперпользователь обходит RLS даже с FORCE — политики «работали», но не действовали. Поэтому рантайм приложения подключается только под непривилегированной ролью `app` (создаётся миграцией 0001: LOGin, GRANT CRUD + default privileges, без BYPASSRLS), а DDL/миграции идут под владельцем схемы `audit`. Двa URL: `DATABASE_URL` (app) и `DATABASE_URL_OWNER` (миграции, сид глобальных справочников — например, системных пресет-ролей, чью запись RLS-политика для app запрещает). Правило для новых таблиц: доменные — ENABLE+FORCE RLS с политикой tenant_isolation в той же миграции; справочники с глобальными строками (tenant_id NULL) — ENABLE без FORCE, сид глобальных строк под owner; журналы — дополнительно REVOKE UPDATE/DELETE от app (append-only).
