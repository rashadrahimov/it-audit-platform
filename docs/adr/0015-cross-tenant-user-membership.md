# Cross-tenant пользователи через Membership

По ответу клиента аудит-команда может быть как внутренней (сотрудники группы), так и внешней фирмой, обслуживающей несколько групп. Поэтому User↔Tenant — **много-ко-многим через сущность Membership** (user, tenant, role/scope). Оба сценария покрываются одной моделью: внутренняя команда = membership в одном тенанте; внешняя фирма/MSP = memberships в нескольких.

Не отменяет [[0003-shared-db-postgres-rls]]: RLS остаётся per-tenant на данных. Активный тенант ставится в контексте запроса; пользователь видит только тенанты своих membership'ов, а RLS ограничивает выборку активным тенантом. **Аутентификация глобальная** (один аккаунт/профиль пользователя с именем, сертификатами), **авторизация — per-membership** (роль и права зависят от тенанта). Приглашение пользователя = создание Membership (существующий аккаунт получает доступ к ещё одному тенанту, либо заводится новый).
