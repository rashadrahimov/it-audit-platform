# ADR-0020: Field-level права как оверлей поверх матрицы (SEC-04)

## Контекст

RBAC ([[0013-rbac-permission-matrix]]) даёт права на уровне **(ресурс, действие) → none/view/edit**. Некоторые аудит-сценарии требуют более тонкой грануляции: скрыть/сделать read-only **отдельные поля** сущности для части ролей. Пример: рекомендация аудитора (`finding.recommendationI18n`) не должна быть видна роли-респонденту до финализации; персональные поля профиля скрыты от не-HR ролей.

## Решение

Field-level права — **необязательный оверлей** поверх матрицы, а не замена:

- Таблица `field_permission`: `(roleId, entityType, field, level)`, где `level ∈ {hidden, view, edit}`.
- **Отсутствие строки = наследование**: поле подчиняется entity-level праву роли (обратная совместимость — существующие роли/эндпоинты не меняются).
- **hidden** — поле вырезается из сериализованного ответа (read) и запрещено на запись.
- **view** — поле видно, но запись отклоняется.
- **edit** — поле видно и записываемо (как если бы оверлея не было).

RLS `field_permission` — по паттерну `role_permission` (глобальные системные роли читаемы всеми; тенантские — в контексте тенанта).

## Enforcement

- **Чтение**: чистый хелпер `maskFields(obj, levels)` вырезает `hidden`-поля перед отдачей. Применяется точечно в сервисах, отдающих сущность (эталон — `finding`).
- **Запись**: `rejectedWriteFields(input, levels)` возвращает поля во входе, чей уровень не `edit` (и явно ограничен) → 403, если непусто.
- Резолв: `RbacService.fieldLevels(userId, tenantSlug, entityType)` → `Record<field, level>` по роли membership'а.

## Последствия

- Оверлей опциональный и адресный: заводится только там, где нужно, остальное работает как раньше.
- Пер-эндпоинтное применение (не глобальный интерцептор) — осознанно: избегаем сквозного рефлективного маскирования всех ответов (риск утечки/поломки), включаем поле-за-полем на реальных сущностях. Эталон — `finding.recommendationI18n`.
- Полное покрытие всех сущностей — итеративно, по мере потребности (не разом).
